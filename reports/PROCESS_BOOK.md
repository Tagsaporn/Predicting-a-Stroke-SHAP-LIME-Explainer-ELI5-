## 1. ภาพรวมและเป้าหมาย

เป้าหมายสามชั้นของโปรเจกต์:

| ชั้น | คำถาม | ผลลัพธ์ที่ต้องการ |
|---|---|---|
| **Data** | ปัจจัยใดสัมพันธ์กับ stroke? | หลักฐานเชิงสถิติที่มี effect size กำกับ |
| **Model** | จำแนกได้ดีแค่ไหนภายใต้ imbalance? | การเปรียบเทียบที่เป็นธรรมและ metric ที่เหมาะสม |
| **XAI** | ทำไมโมเดลจึงทำนายเช่นนั้น และเชื่อได้แค่ไหน? | คำอธิบาย global + local + การตรวจสอบไขว้ |

จุดยืนสำคัญ: **โปรเจกต์นี้ไม่ใช่การสร้างเครื่องมือวินิจฉัย** แต่เป็นการสาธิตกระบวนการ
วิเคราะห์ข้อมูลสุขภาพอย่างมีวินัย พร้อมตระหนักถึงข้อจำกัดของทุกขั้นตอน

## 2. การตั้งคำถามวิจัย

### เหตุผลของการตั้ง Q1–Q5

การตั้งคำถามที่ดีต้อง **(ก)** ตอบได้ด้วยข้อมูลที่มี **(ข)** มีเครื่องมือที่เหมาะสมรองรับ
**(ค)** นำไปสู่การตัดสินใจที่ actionable

| # | คำถามวิจัย | ทำไมต้องถาม |
|---|---|---|
| **Q1** | ปัจจัยใดสัมพันธ์กับ stroke อย่างมีนัยสำคัญ? | เป็นรากฐานของทุกอย่าง — ถ้าไม่รู้ว่าอะไรสัมพันธ์ จะสร้างโมเดลอย่างมีเหตุผลไม่ได้ และต้องแยก "สัมพันธ์" ออกจาก "เป็นสาเหตุ" ให้ชัด |
| **Q2** | ข้อมูลกระจายอย่างไร และ imbalance ส่งผลต่อการเลือก metric อย่างไร? | กำหนด "กติกาการเล่น" ทั้งโปรเจกต์ — ถ้าไม่เข้าใจ imbalance ตั้งแต่ต้น จะเลือก metric ผิดและสรุปผิดทั้งเล่ม |
| **Q3** | โมเดลใดจำแนกได้ดีที่สุดภายใต้ imbalance? | ทดสอบสมมติฐานว่า "โมเดลซับซ้อนกว่าย่อมดีกว่า" เป็นจริงหรือไม่ |
| **Q4** | ฟีเจอร์ใดขับเคลื่อน และทำไม record นี้จึงถูกทำนายเช่นนั้น? | เปลี่ยนจาก "กล่องดำที่แม่น" เป็น "ระบบที่อธิบายได้" ซึ่งจำเป็นในงานสุขภาพ |
| **Q5** | SHAP และ LIME สอดคล้องกันหรือไม่? | **คำถามที่มักไม่มีใครกล้าถาม** — ถ้าคำอธิบายสองวิธีขัดกันเอง เราจะเชื่อคำอธิบายได้อย่างไร? |

### ลำดับการพึ่งพากัน

```
Q2 (เข้าใจข้อมูล) ─→ Q1 (หาความสัมพันธ์) ─→ Q3 (สร้างโมเดล) ─→ Q4 (อธิบายโมเดล) ─→ Q5 (ตรวจสอบคำอธิบาย)
                                              ↑___________________|
                                         (XAI ตรวจสอบย้อนกลับว่าสอดคล้องกับ Q1 ไหม)
```

## 3. การทำความเข้าใจข้อมูล

### 3.1 ลักษณะข้อมูล

ชุดข้อมูลเป็นข้อมูลสุขภาพระดับบุคคลแบบ **cross-sectional** (ไม่มีมิติเวลา)
ประกอบด้วย:

| กลุ่มตัวแปร | คอลัมน์ | ชนิด |
|---|---|---|
| ประชากร | `gender`, `age`, `ever_married`, `work_type`, `Residence_type` | กลุ่ม / ต่อเนื่อง |
| สุขภาพ | `hypertension`, `heart_disease`, `avg_glucose_level`, `bmi` | ไบนารี / ต่อเนื่อง |
| พฤติกรรม | `smoking_status` | กลุ่ม |
| **เป้าหมาย** | `stroke` | ไบนารี |

### 3.2 การตรวจคุณภาพข้อมูล

เราสร้าง `data_quality_report()` ที่ให้ผลอัตโนมัติ: ชนิดข้อมูล, จำนวน/เปอร์เซ็นต์ค่าที่หาย,
จำนวนค่าที่ไม่ซ้ำ และตัวอย่างค่า → บันทึกเป็น `reports/tables/t_data_quality_raw.csv`

**สิ่งที่พบ:**

| ประเด็น | ปริมาณ | ผลกระทบ |
|---|---|---|
| `stroke = 1` | 249 / 5,110 (4.87%) | **imbalance รุนแรง 19.5 : 1** |
| `bmi` หาย | 201 (3.93%) | ต้อง impute อย่างระวัง |
| `gender = "Other"` | 1 ราย | ไม่มีอำนาจทางสถิติ |
| `smoking_status = "Unknown"` | 1,544 (30.22%) | **ตัวแปรสำคัญมี missing ซ่อนอยู่ 30%** |
| `id` | ไม่ซ้ำทุกแถว | ไม่มีข้อมูลเชิงทำนาย |

> **Insight ตั้งแต่ยังไม่วิเคราะห์**: การที่ 30% ของ `smoking_status` เป็น "Unknown"
> เป็นสัญญาณเตือนตั้งแต่ต้นว่า **บทบาทของการสูบบุหรี่อาจถูกประเมินต่ำกว่าความจริง**
> (ถ้าคนที่สูบจริงตอบ "Unknown" เป็นสัดส่วนสูง) — ประเด็นนี้ถูกยกไปอภิปรายในข้อจำกัด

## 4. การตัดสินใจเรื่องคุณภาพข้อมูล

ทุกการตัดสินใจถูก implement ใน `src/data_loader.py::basic_clean()` และ **บันทึกไว้ในโค้ด**

### 4.1 ตัดคอลัมน์ `id`

**เหตุผล**: เป็นตัวระบุ ไม่มีความหมายเชิงทำนาย การใส่เข้าไปจะทำให้โมเดลเรียนรู้ noise
(และถ้าเป็น running number อาจสร้าง spurious pattern)

### 4.2 ตัดแถว `gender = "Other"` (1 ราย)

**ทางเลือกที่พิจารณา:**

| ทางเลือก | ข้อดี | ข้อเสีย | เลือก? |
|---|---|---|---|
| ตัดแถวออก | ทำความสะอาด, ไม่มีกลุ่มที่สรุปไม่ได้ | เสียข้อมูล 1 ราย | ✅ |
| รวมกับกลุ่มใกล้เคียง | เก็บข้อมูลไว้ | **บิดเบือนข้อมูล** — ไม่รู้ว่าควรจัดเป็นอะไร | ❌ |
| คงไว้เป็นกลุ่มที่ 3 | เก็บข้อมูล | กลุ่ม n=1 → CI กว้างอนันต์, โมเดล overfit ได้ | ❌ |

เลือกตัด เพราะ **การเก็บข้อมูล 1 แถวไม่ได้มีค่าเท่ากับความถูกต้องของตัวแปร**

### 4.3 `bmi` ที่หาย 3.93% — เติมที่ไหน?

**ทางเลือก:**

| วิธี | ข้อดี | ข้อเสีย | เลือก? |
|---|---|---|---|
| เติม median **ก่อน** แยก train/test | ง่าย | **data leakage** — test set มีผลต่อค่า median | ❌ |
| เติม median **ภายใน Pipeline** | กัน leakage, ป้องกันการ fit บน test | ต้องเข้าใจ sklearn Pipeline | ✅ |
| ลบแถวที่ bmi หาย | ไม่ต้อง impute | เสีย 201 แถว และเกิด selection bias | ❌ |
| โมเดลทำนาย bmi (MICE/kNN) | ละเอียดกว่า | ซับซ้อน, อาจเพิ่ม noise ที่อ้างว่าเป็นข้อมูลจริง | ❌ |

เลือก median imputation ภายใน `SimpleImputer` เพราะ bmi กระจายเบ้ (มี outlier)
median ทนกว่า mean และการทำใน Pipeline รับประกันว่า fit บน train fold เท่านั้น

### 4.4 `smoking_status = "Unknown"`

**ทางเลือก:** (ก) คงไว้เป็น level (ข) ลบทั้งคอลัมน์ (ค) เติมค่าด้วย mode

**เลือก (ก) คงไว้** เพราะ:
- การลบคอลัมน์ทิ้งข้อมูล **69.8%** ที่ยังใช้ได้
- การเติม mode จะ **สร้างข้อมูลปลอมขึ้นมา 30%** ซึ่งอันตรายกว่าการยอมรับว่าไม่รู้
- การคง "Unknown" ไว้ทำให้โมเดล "เห็น" ว่าการไม่ตอบเป็นสถานะหนึ่ง ซึ่งบางครั้งอาจ
  สัมพันธ์กับความเสี่ยง (เช่น กลุ่มที่ไม่สนใจสุขภาพ)

**แต่** เราเพิ่มหมายเหตุในข้อจำกัดว่าการตีความ `smoking_status` ต้องระวังเป็นพิเศษ

## 6. EDA: การค้นหา Insight

### 6.1 กลยุทธ์การสำรวจ

เราสำรวจตามลำดับ **จากกว้างไปแคบ**:

1. **เป้าหมาย** (`stroke`) — ดูการกระจายก่อน เพราะกำหนดทุกอย่างที่ตามมา
2. **ตัวแปรเดี่ยว** (univariate) — ดูรูปร่างการกระจาย, outlier, ค่าที่หาย
3. **สองตัวแปร** (bivariate) — เทียบกับ target แล้วจึงดูระหว่างตัวแปรเอง
4. **หลายตัวแปร** (multivariate) — correlation, กลุ่มเสี่ยงร่วม

### 6.2 Insight จาก EDA

**Insight 1 — ความไม่สมดุลคือประเด็นหลัก ไม่ใช่รายละเอียด**

คลาสบวก 4.87% หมายถึง baseline accuracy 95.13% โดยไม่ต้องใช้โมเดล
→ **Accuracy ไม่ใช่ metric ของโปรเจกต์นี้** ต้องใช้ Recall/F1/PR-AUC แทน
(ดู `figures/eda/01_target_distribution.png`)

**Insight 2 — อายุคือตัวแปรที่แยกกลุ่มได้ชัดที่สุด**

มัธยฐานอายุ: กลุ่ม stroke 71 ปี vs กลุ่มไม่เป็น 43 ปี (ต่างกัน 28 ปี)
→ สัญญาณแรงมากที่สุดในข้อมูล ต้องได้รับการยืนยันด้วย statistical test

**Insight 3 — ภาระความเสี่ยงหลอดเลือดแสดง dose-response**

เมื่อนับจำนวนปัจจัยเสี่ยง (ความดันสูง + โรคหัวใจ) เป็น 0, 1, 2
อัตราการเกิด stroke เพิ่มขึ้นแบบ **ขั้นบันไดชัดเจน**
→ รูปแบบ dose-response เป็นหลักฐานที่แข็งแรงกว่าตัวแปรเดี่ยว
(ดู `figures/eda/07_vascular_risk.png`)

**Insight 4 — ตัวแปรต่อเนื่องทับซ้อนกันมาก**

`avg_glucose_level` และ `bmi` กลุ่ม stroke สูงกว่า *เล็กน้อย* แต่การกระจายทับซ้อนกันมาก
→ ตัวแปรเหล่านี้ **มีนัยสำคัญทางสถิติแต่อำนาจจำแนกรายบุคคลต่ำ** (คาดว่า
ROC-AUC ของแต่ละตัวจะอยู่ราว 0.6–0.65 เท่านั้น)

**Insight 5 — `smoking_status = Unknown` เป็นกลุ่มใหญ่ผิดปกติ (30%)**

ต้องสงสัยว่าเป็น **Missing Not At Random (MNAR)** — เป็นข้อจำกัดของการวิเคราะห์

## 7. การวิเคราะห์ทางสถิติ

### 7.1 ปรัชญาการเลือกการทดสอบ

หลักการ: **เลือกการทดสอบตามธรรมชาติของข้อมูล ไม่ใช่ตามความสะดวก**

| ชนิดตัวแปร | การทดสอบ | เพราะ |
|---|---|---|
| กลุ่ม × ไบนารี | Chi-square | นับความถี่ในตาราง contingency |
| ต่อเนื่อง × ไบนารี | Mann-Whitney U | **ไม่ต้องสมมติ normality** |
| ไบนารี (ความเสี่ยง) | Odds Ratio + 95% CI | สื่อสารเป็น "ความเสี่ยงกี่เท่า" |

### 7.2 ทำไมไม่ใช้ t-test กับตัวแปรต่อเนื่อง

เราตรวจ normality ด้วย **Shapiro-Wilk** ทุกตัวแปรต่อเนื่องทั้งสองกลุ่ม
แล้วบันทึกผลไว้ในคอลัมน์ `normality_rejected` ของตาราง

ถ้าข้อมูลไม่ normal → t-test จะให้ p-value ที่เชื่อถือไม่ได้
**การเลือก non-parametric test โดยมีหลักฐานประกอบ คือความแตกต่างระหว่าง
"ทำตามตำรา" กับ "ทำตามข้อมูล"**

### 7.3 ทำไมต้องรายงาน Effect Size คู่กับ p-value

ข้อมูล 5,000 แถวทำให้ **p-value เล็กเกือบทุกตัวแปร** แม้ความสัมพันธ์จะจางมาก
นี่คือจุดที่นักวิเคราะห์มือใหม่พลาด: เห็น p < 0.001 แล้วสรุปว่า "สำคัญ"

เราจึงรายงานพร้อมกัน:
- **Cramér's V** (มี bias correction ตาม Bergsma 2013) สำหรับตัวแปรกลุ่ม
- **Rank-biserial correlation** สำหรับ Mann-Whitney

แล้วตีความด้วยเกณฑ์ของ Cohen

### 7.4 การปรับ p-value หลายตัวพร้อมกัน

ทดสอบ 10 สมมติฐานที่ α = 0.05 → ความน่าจะเป็นที่จะเจอ false positive อย่างน้อย 1 ตัว
≈ 1 − 0.95¹⁰ ≈ **40%**!

เลือกใช้ **Benjamini-Hochberg (FDR)** แทน Bonferroni เพราะ:
- Bonferroni ควบคุม family-wise error (เข้มเกินไป → เสี่ยง false negative สูง)
- FDR ควบคุมสัดส่วน false discovery ที่ยอมรับได้ → เหมาะกับงาน exploratory
  ที่ต้องการ "คัดตัวเลือก" มากกว่า "ยืนยันข้อสรุปสุดท้าย"

## 8. การสร้างโมเดล

### 8.1 กลยุทธ์การเปรียบเทียบ

ออกแบบ **model zoo** ที่เป็นระบบ ไม่ใช่ลองสุ่มไปเรื่อย ๆ:

```
                        จัดการ imbalance
                    ┌──────────┴──────────┐
              class weight              SMOTE
              ┌─────┴─────┐           ┌───┴───┐
         LogReg          RF         LogReg    RF
              │           │
           XGBoost    LightGBM
         (scale_pos_weight) (class_weight)
```

**ทุกโมเดลใช้ preprocessing ชุดเดียวกัน** เพื่อให้เปรียบเทียบได้อย่างเป็นธรรม
(ถ้าโมเดลหนึ่งได้ scaling อีกตัวไม่ได้ จะไม่รู้ว่าความต่างมาจากอัลกอริทึมหรือ preprocessing)

### 8.2 ทำไม Validation ของ SMOTE ต้องอยู่ใน Pipeline

**สิ่งที่ผิด (และทำกันบ่อย):**

```python
# ❌ ผิด
X_smote, y_smote = SMOTE().fit_resample(X, y)      # oversample ทั้งชุด
X_train, X_test, ... = train_test_split(X_smote, y_smote)
# → test set มี record สังเคราะห์ปนอยู่ -> ประเมินสูงเกินจริง
```

**สิ่งที่ถูก:**

```python
# ✅ ถูก — SMOTE เกิดใน fold ระหว่าง cross-validation เท่านั้น
ImbPipeline([("prep", preprocessor), ("smote", SMOTE()), ("clf", ...)])
```

เราใช้ `imblearn.pipeline.Pipeline` ซึ่ง apply sampler **เฉพาะตอน fit** ไม่ใช่ตอน predict

### 8.3 การเลือก Threshold — หัวใจของปัญหานี้

**ปัญหาที่พบ**: ที่ threshold = 0.5 โมเดลที่ **ยังไม่จัดการ imbalance** (RandomForest,
LightGBM) ให้ Recall **ต่ำมาก (0.12–0.22)** เพราะ probability ของคลาสบวกถูกกดต่ำ
เมื่อ prevalence = 4.87% → probability ส่วนใหญ่ต่ำกว่า 0.5 เกือบทั้งหมด

**วิธีแก้**: หา threshold จาก **Out-of-Fold predictions**

```
1. cross_val_predict(model, X_train, y_train, cv=StratifiedKFold(5))
   → ได้ probability ของแต่ละ record ที่ "โมเดลไม่เคยเห็น record นั้นตอน fit"
2. สร้าง Precision-Recall curve จาก OOF probabilities
3. เลือก threshold ที่ให้ F1 สูงสุด
4. fit โมเดลเต็มบน X_train แล้วประเมินบน X_test ด้วย threshold ขั้นตอนที่ 3
   (พร้อมรายงานผลที่ 0.5 เทียบกันเพื่อให้เห็นขนาดของผล)
```

**ทำไมไม่หา threshold บน test set**: เพราะเท่ากับใช้ test set ในการตัดสินใจ
→ test set ไม่บริสุทธิ์อีกต่อไป ผลที่ได้จะ optimistic เกินจริง

### 8.3.1 สิ่งที่ "คาดไม่ถึง" และเป็นบทเรียนสำคัญ

ตอนแรกเราเขียนสมมติฐานว่าการ tune threshold จะ **เพิ่ม Recall เสมอ** — แต่ผลจริง
**ไม่เป็นเช่นนั้น** และขึ้นกับว่าโมเดลจัดการ imbalance แล้วหรือยัง:

| โมเดล | จัดการ imbalance | Recall@0.5 | Recall (tuned) | ทิศทาง |
|---|---|---|---|---|
| RF (balanced_subsample) | บางส่วน | 0.12 | **0.54** | ↑↑ |
| LightGBM | บางส่วน | 0.18 | **0.44** | ↑↑ |
| RF (SMOTE) | ใช่ | 0.22 | **0.66** | ↑↑ |
| XGBoost | ใช่ | 0.46 | 0.44 | ↓ เล็กน้อย |
| LogReg (balanced) | ใช่ | **0.80** | 0.60 | **↓** |
| LogReg (SMOTE) | ใช่ | **0.80** | 0.70 | **↓** |

**คำอธิบาย**: โมเดลที่ถ่วงน้ำหนักคลาสอยู่แล้วจะดัน probability ของคลาสบวกให้สูง
→ threshold 0.5 ให้ Recall สูงอยู่แล้ว → จุด F1-optimal จึงอยู่สูงกว่า และ
**ลด Recall เพื่อแลก Precision**

> **บทเรียน**: threshold คือ "การเลือกจุดบน PR curve" ตามต้นทุน FN:FP
> **ไม่ใช่ "การปรับให้ดีขึ้น"** และถ้าเป้าหมายคือ Recall สูงสุด การใช้
> โมเดลที่ถ่วงน้ำหนักคลาส + threshold 0.5 ก็ได้ Recall 0.80 แล้ว
> — สิ่งที่ต้องตัดสินใจคือ *ยอมรับ false positive ได้กี่ราย* ต่างหาก
>
> เราจึงแก้ทั้งโค้ดเอกสารและ notebook ให้พูดตรงตามข้อมูล ไม่ใช่ตามสมมติฐานเดิม

### 8.4 Metric ที่เลือกและเหตุผล

| Metric | ใช้วัดอะไร | ทำไมเลือก |
|---|---|---|
| **Recall** | สัดส่วนผู้ป่วยจริงที่ตรวจพบ | พลาดผู้ป่วย (FN) มีต้นทุนสูงที่สุด |
| **F1** | สมดุล Recall–Precision | ใช้เมื่อต้องการตัวเลขเดียว |
| **PR-AUC** | คุณภาพโดยรวมบนคลาสบวก | **ไม่ถูก TN จำนวนมหาศาลกลบ** เหมือน ROC |
| **Specificity** | สัดส่วนคนปกติที่ระบุถูก | ดูต้นทุนการเตือนเกิน |
| **Confusion Matrix** | FN/FP เป็นจำนวนคน | สื่อสารกับแพทย์/ผู้ตัดสินใจได้ตรงที่สุด |
| ~~Accuracy~~ | — | **ไม่ใช้อีกต่อไป** เพราะ baseline = 95% |

## 9. Explainable AI

### 9.1 หลักการ: อธิบายที่ระดับไหน

**ปัญหาที่พบ**: Pipeline ทั้งก้อนรับ DataFrame แต่ SHAP/LIME ต้องการ predict function
ที่รับเมทริกซ์ตัวเลข

**ทางเลือก:**

| ทางเลือก | ข้อดี | ข้อเสีย | เลือก? |
|---|---|---|---|
| อธิบาย Pipeline ทั้งก้อน | สอดคล้องกับการใช้งานจริง | ต้อง wrap, ช้า, ชื่อฟีเจอร์หาย | ❌ |
| อธิบาย classifier บน transformed features | เร็ว, ชื่อฟีเจอร์ชัด, deterministic | ต้องรวม one-hot กลับเอง | ✅ |

**แต่ one-hot ทำให้อ่านยาก**: `work_type_Private`, `work_type_Govt_job`, ...
เราจึงสร้าง `group_onehot_columns()` เพื่อรวมกลับเป็น `work_type`
→ ได้ทั้งความเร็วและความอ่านง่าย

### 9.2 SHAP: การเลือก Explainer

| Explainer | ใช้เมื่อ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **TreeExplainer** | RF, XGBoost, LightGBM | **exact** + เร็วมาก | ใช้กับ linear ไม่ได้ |
| **LinearExplainer** | Logistic/Linear | exact สำหรับ linear model | ใช้ได้เฉพาะ linear |
| KernelExplainer | ทุกโมเดล | ใช้ได้ทั่วไป | ช้ามาก, variance สูง |

เราเลือกแบบ **dispatcher อัตโนมัติ** ตามชนิดโมเดล พร้อม fallback
→ ได้ความแม่นยำของ exact method ไม่ต้องจ่ายราคาด้วยความเร็ว

### 9.3 กับดักที่ค้นพบ: mean(|SHAP|) กับฟีเจอร์ที่หายาก

**สิ่งที่เกิดขึ้น**: ตอนแรกเราแปลกใจว่า `heart_disease` มีค่า `mean(|SHAP|)` ต่ำมาก
ทั้งที่ Odds Ratio ≈ 4.7 และ V = 0.134

**การสอบสวน**: ตรวจ coefficient ของโมเดลโดยตรง

```
heart_disease  coefficient = 0.144   (ค่าบวก มีนัยสำคัญ)
แต่ prevalence = 5.4%  ->  records ส่วนใหญ่มีค่า 0 -> contribution = 0
=> mean|0.144 x (0 หรือ 1)| = 0.144 x 0.054 ≈ 0.008
```

**ข้อสรุป**: ไม่ใช่บั๊ก — `mean(|SHAP|)` **เอนเอียงเข้าข้างฟีเจอร์ที่พบบ่อยโดยธรรมชาติ**

**วิธีแก้**: เพิ่มคอลัมน์ `pct_records_active` และ `mean_abs_shap_when_active`
เพื่อรายงานอิทธิพล "เฉพาะเมื่อฟีเจอร์เปิด" คู่กันเสมอ
→ **บทเรียน: ค่า statistical importance ต้องตีความตามบริบทของการวัด**
ถ้าไม่เข้าใจที่มาของสูตร อาจรายงานผิดว่าปัจจัยเสี่ยงสำคัญ "ไม่สำคัญ"

### 9.4 กับดักที่สอง: หน่วยของค่า SHAP

| Explainer / โมเดล | หน่วยที่ได้ |
|---|---|
| TreeExplainer + RandomForest (sklearn) | probability (0–1) |
| TreeExplainer + XGBoost/LightGBM | **log-odds (margin)** |
| LinearExplainer + LogisticRegression | **log-odds (margin)** |

ตรวจ additivity ผิดหน่วย → ค่าต่างกันมหาศาลและเข้าใจผิด
เราจึงเพิ่มฟังก์ชัน `shap_space()` และบันทึกหน่วยไว้ใน `reports/metrics.json`

### 9.5 กับดักที่สาม: confounding ทำให้เครื่องหมายกลับ

**สิ่งที่พบ**: `ever_married` มีค่าเฉลี่ย SHAP **เป็นลบ** (ดันไปทาง "ไม่เป็น stroke")
แต่การทดสอบทางสถิติบอกว่าคนสมรสแล้วมีอัตรา stroke **สูงกว่า**

**การอธิบาย**: **Simpson's paradox / confounding by age**
- ในข้อมูลดิบ: คนสมรสแล้วอายุมากกว่า → stroke สูงกว่า
- ในโมเดล: โมเดล **ควบคุมอายุแล้ว** → ในกลุ่มอายุเท่ากัน การสมรสไม่เพิ่มความเสี่ยง

**บทเรียน**: **static correlation ≠ model attribution**
ทั้งสองถูกต้องแต่ตอบคนละคำถาม:
- Statistical test ตอบ "อะไรสัมพันธ์กับผลลัพธ์ในข้อมูล"
- SHAP ตอบ "โมเดลใช้ข้อมูลนี้อย่างไรในการตัดสิน"

### 9.6 LIME: จุดประสงค์คือ cross-check

เราไม่ได้ใช้ LIME เพื่อแทน SHAP แต่เพื่อ **ตรวจสอบว่า SHAP น่าเชื่อถือหรือไม่**
ถ้าสองวิธีที่ใช้ทฤษฎีต่างกันชี้ทางเดียวกัน → มั่นใจขึ้น
ถ้าขัดกัน → ต้องระวังและรายงานความไม่แน่นอนนั้น

**ข้อควรระวังที่บันทึกไว้:**
- LIME เป็น **stochastic** → ต้องตั้ง `random_state`
- LIME **discretize** ตัวแปรต่อเนื่อง (`age <= 45`) → สูญเสียความละเอียด
- ขนาดอิทธิพลของสองวิธี **ไม่เทียบกันตรง ๆ ได้** → ใช้ **Spearman (อันดับ)** ไม่ใช่ Pearson

### 9.7 การวัดความสอดคล้อง

| ตัวชี้วัด | วัดอะไร | เกณฑ์ |
|---|---|---|
| `overlap_count` | จำนวนฟีเจอร์ร่วมใน top-8 | ≥ 4 จาก 8 |
| `jaccard_topk` | ความคล้ายของเซต top-k | ≥ 0.30 |
| `spearman_rho` | ความสอดคล้องของ *ขนาด* | ≥ 0.50 |
| `sign_agreement` | ทิศทาง (+/−) ตรงกัน | ≥ 0.70 |

**การปรับปรุงที่ทำ**: ตอนแรกคำนวณ Spearman เฉพาะฟีเจอร์ที่อยู่ใน top-k ของ *ทั้งคู่*
ทำให้เหลือจุดไม่ถึง 3 จุด → ค่าเป็น NaN เกือบทั้งหมด
แก้เป็นคำนวณบน **ฟีเจอร์ทั้งหมดที่ทั้งสองวิธีให้ค่า** → ได้ค่าที่เสถียรจริง

## 13. ข้อจำกัด

### ข้อจำกัดของข้อมูล

1. **Cross-sectional** — ไม่มีมิติเวลา → สรุปได้แค่ *ความสัมพันธ์* ไม่ใช่ *causation*
2. **ไม่มีตัวแปรสำคัญหลายตัว** — ประวัติครอบครัว, การออกกำลังกาย, อาหาร, ยาที่ใช้,
   ความเครียด, รายได้ → **omitted variable bias**
3. **`smoking_status = Unknown` 30%** — อาจเป็น MNAR → ประเมินบทบาทการสูบบุหรี่ต่ำกว่าจริง
4. **`bmi` หาย 3.93%** — เติมด้วย median ทำให้ variance ของ bmi ลดลง (underestimate)
   และลดความสัมพันธ์กับ target
5. **แหล่งข้อมูลไม่ชัดเจน** — ไม่ทราบวิธีการเก็บ (self-report? วัดจริง?) จึงประเมิน
   measurement bias ไม่ได้

### ข้อจำกัดของโมเดล

6. **คลาสบวกน้อย (249 ราย)** — test set มีเพียง 50 ราย → metric variance สูง
   (ผู้ป่วย 1 ราย = 2% ของ Recall)
7. **ไม่มี external validation** — ผลอาจไม่ generalize กับประชากรอื่น
8. **ไม่มี temporal validation** — ไม่รู้ว่าโมเดล stable ข้ามเวลาไหม
9. **ไม่ทดสอบ fairness** — ยังไม่ได้ประเมินว่าโมเดลแม่นเท่ากันในทุกกลุ่มเพศ/อาชีพ
   ซึ่งสำคัญมากในงานสุขภาพ
10. **ไม่มีการ calibrate probability** — probability ที่ได้อาจไม่ตรงกับความถี่จริง
    (สำคัญถ้าจะใช้ค่าความน่าจะเป็นในการตัดสินใจ เช่น จัดลำดับความเร่งด่วน)

### ข้อจำกัดของ XAI

11. **SHAP อธิบายโมเดล ไม่ได้อธิบายโรค** — ค่า SHAP บอกว่าโมเดลใช้ฟีเจอร์อย่างไร
12. **ฟีเจอร์ correlated** — SHAP กระจายเครดิตอย่างไม่แน่นอนระหว่างฟีเจอร์ที่สัมพันธ์กัน
    (เช่น age กับ ever_married) คำอธิบายของแต่ละตัวจึงผันผวนได้
13. **ค่า SHAP ขึ้นกับ background dataset** — เปลี่ยนชุดอ้างอิง ค่าเปลี่ยน
14. **LIME เป็น stochastic และ discretize** — ผลไม่ซ้ำเดิม 100% และสูญเสียความละเอียด
15. **one-hot grouping เป็นการประมาณ** — ผลรวมของ one-hot ไม่เท่ากับ SHAP
    ของตัวแปรกลุ่มในความหมายเข้มงวด
16. **Correlation between XAI methods ≠ correctness** — การที่ SHAP และ LIME
    เห็นตรงกันไม่ได้พิสูจน์ว่าคำอธิบาย "ถูก" เพียงแต่ว่า "สอดคล้องกัน"

## 14. บทเรียนและสิ่งที่ทำต่อได้

### บทเรียนหลัก

1. **เข้าใจข้อมูลก่อนเลือกเครื่องมือ** — ถ้าเริ่มจาก "จะใช้ XGBoost" เราจะพลาดว่า
   โมเดลเชิงเส้นเพียงพอ และอาจเลือก metric ผิดตั้งแต่ต้น
2. **Metric ต้องเลือกตามบริบท** — Accuracy ใช้ไม่ได้กับข้อมูลไม่สมดุล
   และ "โมเดลที่ดีที่สุด" ไม่มีคำตอบเดียวถ้าไม่ระบุเกณฑ์
3. **Threshold เป็น hyperparameter ที่ถูกลืม — แต่ต้องเข้าใจว่ามันทำอะไร** —
   หลายโปรเจกต์ tune model แต่ใช้ 0.5 ตามค่าเริ่มต้น ในที่นี้การ tune threshold
   เปลี่ยน Recall ของ RandomForest จาก 0.12 → 0.54 **แต่ก็ทำให้ Recall ของ
   LogReg (ที่ถ่วงน้ำหนักแล้ว) ลดจาก 0.80 → 0.60** เพราะมันคือการเลือกจุดบน
   PR curve ตามต้นทุน FN:FP ไม่ใช่การปรับให้ดีขึ้นโดยอัตโนมัติ
4. **ระวัง leakage ทุกจุด** — imputation, scaling, sampling, threshold tuning
   ทุกอย่างต้อง fit บน train เท่านั้น
5. **ค่า importance ต้องตีความตามสูตรของมัน** — `mean(|SHAP|)` เอนเอียงเข้าข้าง
   ฟีเจอร์ที่พบบ่อย การรู้ที่มาของสูตรสำคัญพอ ๆ กับการรู้วิธีใช้
6. **XAI ไม่ใช่คำตอบสุดท้าย** — เป็นเครื่องมือตรวจสอบ ถ้าสองวิธีขัดกัน
   นั่นคือ *ข้อมูล* ไม่ใช่ *ปัญหา*
7. **ความสัมพันธ์ ≠ คำอธิบายของโมเดล** — Simpson's paradox เตือนเราว่า
   ต้องแยกให้ชัดว่ากำลังตอบคำถามอะไร

### สิ่งที่ทำต่อได้

| ลำดับ | งาน | คุณค่า |
|---|---|---|
| 1 | **Probability calibration** (Platt/isotonic) + reliability curve | ให้ค่าความน่าจะเป็นใช้ตัดสินใจได้จริง |
| 2 | **Repeated stratified CV + bootstrap CI** | ระบุช่วงความเชื่อมั่นของ metric |
| 3 | **Fairness audit** แยกตามกลุ่มเพศ/อาชีพ | ตรวจว่าคำอธิบายและความแม่นยำเป็นธรรม |
| 4 | **Interaction effects** (SHAP interaction values, PDP/ICE) | เข้าใจผลร่วมระหว่างอายุ × ความดัน |
| 5 | **Cost-sensitive learning** กำหนดต้นทุน FN:FP จริง | เลือก threshold ตามเศรษฐศาสตร์สุขภาพ |
| 6 | **Missing data sensitivity analysis** — ทดลองลบ `smoking_status` | วัดว่าข้อจำกัด Unknown 30% กระทบผลแค่ไหน |
| 7 | **External / temporal validation** | ยืนยันว่า generalize ได้ |
| 8 | **Counterfactual explanation** (DiCE) | "ถ้าลดความดันได้ ความเสี่ยงจะลดเท่าไร" — actionable กว่า SHAP |
